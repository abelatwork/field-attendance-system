# Field Student Attendance System

# Attendance Rules

# 1. Introduction

The Field Student Attendance Tracking System records when registered field students enter and leave their assigned field activities.

Attendance is recorded using two actions:

- IN
- OUT

The system validates each attendance action before saving it.

---

# 2. Student Registration Requirement

Only students registered by the Super Admin can record attendance.

A student must:

1. Exist in the student database.
2. Be active.
3. Be available through the attendance search interface.

Unregistered students cannot create their own attendance records.

---

# 3. Student Identification

Students are selected through the attendance page by searching for their name.

The system must use the student's unique database ID when creating an attendance record.

The student's name must not be used as the primary identifier for an attendance record because two or more students may have the same name.

The selected student's database ID is sent to the backend when attendance is submitted.

---

# 4. IN Attendance

An `IN` action indicates that a student has entered or started their field activity.

An IN record can be created when the student is currently not considered IN.

### Valid IN

An IN action is valid when:

- The student exists.
- The student is active.
- The student is not currently IN.
- A valid location is provided.
- The attendance request passes backend validation.

### Duplicate IN

A student must not create another IN record while they already have an active IN status.

For example:

```text
Student status: IN
New action: IN
Result: Rejected
```

---

# 5. OUT Attendance

An OUT action indicates that a student has finished or left their field activity.

An OUT record can only be created when the student currently has an active IN status.

#### Valid OUT

An OUT action is valid when:

- The student exists.
- The student is active.
- The student currently has an active IN status.
- A valid location is provided.
- The attendance request passes backend validation.

#### OUT Without IN

A student must not record OUT when there is no active IN attendance.

For example:

```
Student status: OUT / no active IN
New action: OUT
Result: Rejected
```

This prevents an invalid attendance sequence.

---

# 6. Attendance Sequence

The expected attendance sequence is:

`IN → OUT → IN → OUT → ...`

A student may record another IN after successfully recording an OUT.

Example:

```
08:00  IN
16:30  OUT
08:10  IN
17:00  OUT
```

The exact times depend on when the student submits their attendance.

---

# 7. Server Timestamp

Attendance timestamps must be generated by the backend server.

The student browser must not be trusted to determine the official attendance time.

When a valid attendance request reaches the backend, the server records the current timestamp.

Example:

```
Student submits attendance
        ↓
Backend receives request
        ↓
Backend validates request
        ↓
Server generates timestamp
        ↓
Attendance record is saved
```

This helps prevent users from manipulating the recorded attendance time through their device clock.

---

# 8. Location Requirement

Location is required when recording attendance in the v1.0.0 system.

The frontend uses the browser's Geolocation API to obtain the student's current location.

The location information includes:

- Latitude
- Longitude
- Accuracy

Example:

```
Latitude:  -6.xxxxx
Longitude: 39.xxxxx
Accuracy:  10 metres
```

The location is sent to the backend together with the attendance action.

---

# 9. Location Permission

The student's browser must request permission to access the device location.

If location permission is denied, the attendance submission should not proceed.

Example:

```
Location permission granted
        ↓
Location captured
        ↓
Attendance submitted
```

If permission is denied:

```
Location permission denied
        ↓
Attendance submission stopped
        ↓
Student is informed that location is required
```

---

# 10. Location Accuracy

The browser provides an accuracy value together with latitude and longitude.

The system stores this accuracy value as part of the attendance record.

The v1.0.0 system records the accuracy information but does not enforce a specific maximum accuracy threshold.

For example, an attendance record may contain:

```
Latitude:  -6.xxxxx
Longitude: 39.xxxxx
Accuracy:  25 metres
```

Future versions may introduce location-quality requirements or geofencing.

# 11. Attendance Record

Each successful attendance action creates an attendance record associated with a specific student.

The record contains:

- Attendance ID
- Student ID
- Attendance type
- Server timestamp
- Latitude
- Longitude
- Location accuracy

The Student ID establishes the relationship between the attendance record and the registered student.

# 12. Active and Inactive Students

Only active students should be able to record attendance.

When a student becomes inactive, the student should no longer appear as an available student for normal attendance recording.

Historical attendance records should remain in the database.

The preferred approach is to deactivate a student instead of permanently deleting the student.

# 13. Attendance History

Attendance records should be preserved as historical records.

The system should maintain the relationship between each attendance record and the student who created it.

Attendance history can therefore be used by authorized users to monitor student attendance.

Supervisors can view attendance for their assigned students.

Super Admins can view attendance information across the system.

# 14. Supervisor Access

A Supervisor can view attendance information for students assigned to them.

A Supervisor cannot create, edit, or delete attendance records through the management portal.

The system must ensure that a Supervisor cannot access attendance information belonging to students outside their assigned group.

# 15. Super Admin Access

The Super Admin can view attendance records across the system.

The Super Admin manages student records and supervisor assignments.

Attendance validation rules still apply when attendance is recorded by students.

# 16. Invalid Attendance Requests

The backend must reject invalid attendance requests.

Examples include:

### Student does not exist

```
Result: Rejected
Reason: Student is not registered
```

### Student is inactive

```
Result: Rejected
Reason: Student is inactive
```

### Duplicate IN

```
Current status: IN
Requested action: IN
Result: Rejected
```

### OUT without IN

```
Current status: OUT / no active IN
Requested action: OUT
Result: Rejected
```

### Missing location

```
Location: Missing
Result: Rejected
```

Invalid requests must not create attendance records in the database.

# 17. Attendance Validation Flow

The basic attendance validation process is:

```
Student selects name
        ↓
Student selects IN or OUT
        ↓
Browser requests location
        ↓
Location captured
        ↓
Request sent to backend
        ↓
Is student registered?
       / \
     No   Yes
     ↓      ↓
 Reject   Is student active?
             / \
           No   Yes
           ↓      ↓
         Reject  Validate IN/OUT
                    ↓
              Is action valid?
                 /      \
               No        Yes
               ↓          ↓
            Reject    Save attendance
                          ↓
                   Generate server time
                          ↓
                    Return success
```

---

# 18. Attendance Confirmation

After a successful attendance submission, the student should receive a clear confirmation message.

The confirmation should indicate that the attendance was successfully recorded.

Example:

```
Attendance recorded successfully.

Status: IN
Time: 08:15
```

The exact interface design may change as the frontend develops.

# 19. No Manual Timestamp

Students must not be allowed to manually enter the official attendance time.

The official timestamp is generated by the backend server.

This ensures that the attendance system has a consistent source of time.

# 20. No Manual Location Entry

Students should not manually type latitude or longitude into the attendance form.

The location should be obtained through the browser's Geolocation API.

This reduces the possibility of users entering arbitrary coordinates.

# 21. Data Integrity

Attendance records should not be silently overwritten.

Each successful attendance action represents a historical event.

The system should preserve:

- Student association
- IN/OUT action
- Server timestamp
- Location
- Location accuracy

This allows authorized users to review attendance history accurately.

# 22. The Scope of v1.0.0

The v1.0.0 attendance system includes:

- IN and OUT attendance.
- Registered students only.
- Active student validation.
- Duplicate IN prevention.
- OUT-without-IN prevention.
- Server-generated timestamps.
- Browser-based location capture.
- Latitude and longitude storage.
- Location accuracy storage.
- Attendance history.
- Supervisor attendance viewing.
- Super Admin attendance viewing.

The following are outside the v1.0.0 scope:

- Geofencing.
- Automatic location verification against a fixed field site.
- Attendance reports and analytics.
- Notifications.
- SMS or email alerts.
- Attendance export.
- Mobile application.
- Biometric verification.
- Facial recognition.
- AI-based attendance verification.

These features may be considered in future versions.
